# 需求文档生成设计文档规范

> 版本：v1.0<br>
> 适用范围：CNAPS Single-Table POC 及结构相近的后端需求<br>
> 示例输入：`docs/requirements/cnaps-review-requirements.md`<br>
> 示例输出：`docs/design/cnaps-review-design.md`

## 1. 目的

本规范用于把需求文档稳定地转换为可评审、可实现、可验证的设计文档。设计过程必须做到：

- 每条需求都有设计落点和验证方式。
- 每项设计都能追溯到需求、项目约束或已核验的现有实现。
- 明确区分事实、设计决策、假设和待确认项，不把推测写成结论。
- 在编码前发现范围膨胀、接口冲突、状态遗漏、并发风险和环境限制。
- 输出足够具体，使实现人员不需要再次猜测修改位置、处理顺序和完成标准。

## 2. 输入与优先级

生成设计前必须固定输入版本，并按以下优先级处理冲突：

1. 仓库级约束，如 `AGENTS.md`、安全规则和任务明确限制。
2. 本次需求文档。
3. 已批准的架构、数据、接口或领域规范。
4. 当前分支中的实际代码、配置、数据库脚本和构建方式。
5. 补充 API 文档；仅补充更高优先级输入没有定义的细节。
6. 历史设计、历史代码和口头信息；只能作为参考，不能覆盖当前事实。

输入清单至少包含：

| 输入 | 必需 | 需要记录的内容 |
| --- | :---: | --- |
| 需求文档 | 是 | 路径、版本、日期 |
| 项目约束 | 是 | 允许与禁止修改的范围 |
| 当前代码基线 | 是 | 分支或提交、工作区是否有未提交修改 |
| 相关接口文档 | 条件必需 | 仅记录实际引用章节 |
| 数据模型或字段定义 | 条件必需 | 表、字段、类型、约束、时间来源 |
| 构建与验证方式 | 是 | 命令、执行顺序、环境前提 |

若输入之间冲突，不得静默选择。设计文档必须在“冲突与待确认项”中记录冲突、采用结论、依据和影响；无法安全决定时停止进入实现阶段。

## 3. 信息分类

分析和写作时，为每项关键信息标记来源类型：

| 类型 | 含义 | 写作要求 |
| --- | --- | --- |
| `REQ` | 需求明确要求 | 设计必须覆盖，不得弱化 |
| `CONSTRAINT` | 项目或任务约束 | 写入设计边界及验证门禁 |
| `AS-IS` | 已从当前代码核验的事实 | 写明文件、类、函数或配置位置 |
| `DECISION` | 为满足需求作出的设计决策 | 写明原因、影响和备选方案（如有） |
| `ASSUMPTION` | 尚未被输入证明的假设 | 必须显式列出并给出确认方式 |
| `TBD` | 当前无法确定的问题 | 指定负责人或确认条件；未关闭前不得宣称设计可实施 |

禁止使用“应该已有”“大概复用”“预计无需修改”等模糊表述替代代码核验。

## 4. 标准流程

### 4.1 阶段一：固定范围和基线

1. 记录需求版本、相关文档版本、当前分支或提交。
2. 读取仓库约束，整理允许修改文件、禁止项和验证命令。
3. 检查工作区状态，区分已有用户改动和本任务范围。
4. 从需求的“目标、范围、不实现、完成标准”形成范围基线。

阶段产物：输入清单、范围内清单、范围外清单、基线信息。

### 4.2 阶段二：需求原子化

把需求拆成单一、可验证的原子需求，并分配稳定编号。推荐编号：

```text
FR-001   功能需求
API-001  接口契约
BR-001   业务或状态规则
DATA-001 数据与审计规则
NFR-001  并发、性能、安全等非功能需求
ERR-001  错误处理
CON-001  范围或实现约束
ACC-001  验收标准
```

每条原子需求只表达一个结果。例如“校验状态、更新版本并返回摘要”应拆成状态校验、乐观锁更新、响应字段三个需求。

阶段产物：需求追踪矩阵的需求侧内容。

### 4.3 阶段三：核验当前实现

按调用链从入口到持久化逐层核验，不只根据文件名推断：

```text
HTTP 路由
 -> 请求解析与可信上下文注入
 -> 服务映射
 -> 中间件接口元数据
 -> 原生服务
 -> 事务与数据库访问
 -> 响应字段映射
 -> HTTP 状态映射
```

对每层记录：

- 可直接复用的现有能力。
- 需要修改或新增的能力。
- 明确无需修改但影响方案成立的能力。
- 文件、符号、配置块和安全编辑锚点。
- 与需求不一致的现状及迁移影响。

阶段产物：现状说明和差距清单。没有完成现状核验，不进入详细设计。

### 4.4 阶段四：形成设计决策

先解决跨层决策，再写逐文件设计。至少覆盖：

- 接口路径、方法、请求、响应和错误契约。
- 服务复用或新增策略及命名。
- 状态机、前置条件和非法转换。
- 服务端可信字段及客户端不可控字段。
- 数据写入、审计字段、时间来源和版本规则。
- 事务边界、并发控制、回滚条件和幂等性。
- 兼容性、部署配置及范围外影响。

重要决策使用以下格式：

```text
决策：复用或新增什么能力。
依据：对应需求编号和已核验现状。
影响：涉及的层、文件和兼容性。
排除：明确不采用的方案及原因。
```

### 4.5 阶段五：编写执行级设计

逐文件描述修改，必须回答：

1. 为什么修改该文件。
2. 修改哪个类、函数、SQL、配置块或锚点。
3. 输入、处理顺序、输出和异常路径是什么。
4. 哪些既有顺序、字段、元数据或行为必须保持不变。
5. 如何验证该文件的改动没有越界。

代码片段只用于消除歧义。通用设计文档不应复制完整实现；涉及脆弱配置、严格调用顺序、事务处理或精确响应字段时，可以给出最小必要伪代码或补丁示意。

### 4.6 阶段六：闭环追踪与评审

完成设计后补齐需求追踪矩阵：

| 需求 ID | 来源 | 设计落点 | 代码或配置落点 | 验证方式 | 状态 |
| --- | --- | --- | --- | --- | --- |
| `API-001` | 需求 §3 | 设计 §4.1 | Servlet 路由、服务映射 | 路由测试或静态检查 | 已覆盖 |

执行两个方向的检查：

- 正向追踪：每条需求是否都有设计、实现落点和验证方式。
- 反向追踪：每项设计是否有来源，是否出现需求外扩展。

只有追踪矩阵无遗漏、无无来源设计，且所有阻塞性 `TBD` 已关闭，设计才可进入实现。

## 5. 设计文档标准目录

设计文档默认使用以下结构；不适用章节可标记“不涉及”，不要直接删除导致评审遗漏。

```text
# <功能名称>设计

> 设计版本、日期、需求文档及版本、代码基线、状态

## 1. 目标与范围
## 2. 输入依据与优先级
## 3. 现状与差距
## 4. 总体方案和关键决策
## 5. 接口设计
## 6. 状态与业务规则
## 7. 数据、审计与事务设计
## 8. 分层调用链和逐文件设计
## 9. 错误处理与响应映射
## 10. 并发、幂等、安全和兼容性
## 11. 配置、构建与发布影响
## 12. 验证方案与验收标准
## 13. 需求追踪矩阵
## 14. 风险、假设、冲突与待确认项
## 15. 明确不修改项
```

### 5.1 设计粒度

设计至少达到以下粒度：

- 路由：明确 HTTP 方法、精确路径和匹配顺序。
- 字段：明确来源、类型、必填性、默认值、覆盖规则和返回范围。
- 状态：明确当前状态、动作、目标状态和失败码。
- 数据：明确查询条件、更新字段、时间来源、版本条件和影响行数语义。
- 事务：明确开始、提交、回滚和提交前重读顺序。
- 错误：明确业务码、HTTP 状态及产生层级。
- 配置：明确服务声明、导出、注册、接口元数据及唯一性要求。
- 验证：明确静态检查、构建命令、测试范围、顺序和预期结果。

## 6. CNAPS 审核需求的示范映射

对 `docs/requirements/cnaps-review-requirements.md`，设计生成时应先得到以下核心映射：

| 需求主题 | 设计结论 | 主要落点 |
| --- | --- | --- |
| 待审核列表 | 复用 `CNAPS4609Q`，服务端强制待审核状态 | Servlet、RequestMapper |
| 审核动作 | 只新增 `CNAPS5702A/R`，共用审核函数 | RequestMapper、`cnaps_review.c`、服务配置 |
| 状态规则 | 仅待审核可通过或退回 | 原生服务状态校验 |
| 可信上下文 | 操作员、机构、请求号由 WebFE 覆盖 | 请求映射及原生服务读取 |
| 审计时间 | 由 Oracle `SYSTIMESTAMP` 生成 | `db_helper.c` |
| 并发 | `BILL_ID + VERSION_NO` 乐观锁，0 行映射 `3004` | 数据库更新、事务处理 |
| 动作响应 | 只返回六个摘要字段 | FML32 输出及现有响应映射 |
| 范围约束 | 不新增查询服务、表、字段、前端和依赖 | 文件清单、明确不修改项、结构检查 |

完整执行级细节见 `docs/design/cnaps-review-design.md`。该示例体现了三个关键原则：优先复用现有链路、把跨层配置纳入设计、把禁止项转换为可执行的结构检查。

## 7. 质量门禁

### 7.1 内容门禁

- [ ] 需求、约束、API 和代码基线均有版本或路径。
- [ ] 范围内、范围外和明确不修改项均已列出。
- [ ] 每条原子需求在追踪矩阵中恰好有一行。
- [ ] 所有新增设计都有来源，没有擅自扩展功能。
- [ ] 当前实现的复用结论均已定位到具体符号或配置。
- [ ] API、状态、字段、事务、并发、错误和审计形成闭环。
- [ ] 成功路径、失败路径和并发路径均有验证方式。
- [ ] 所有假设和待确认项显式列出。

### 7.2 可实施性门禁

- [ ] 修改文件清单完整，且未超出允许范围。
- [ ] 逐文件设计包含准确锚点和保持不变项。
- [ ] 新服务在代码声明、构建、运行配置和接口元数据中均有落点。
- [ ] 字段从 HTTP 到数据库再到响应的映射完整。
- [ ] 验证命令适配实际环境，并按低成本到高成本排序。
- [ ] 环境缺失不会被误判为业务设计错误。

### 7.3 发布前判定

出现以下任一情况，设计状态必须标记为“待确认”，不得直接交给自动实现：

- 需求与更高优先级约束冲突。
- 关键接口、字段、状态或错误码未定义。
- 当前代码不存在设计所依赖的复用能力。
- 数据库事务或并发语义无法从现状确认。
- 修改范围将超出需求授权。

## 8. 设计变更规则

- 需求版本变化后，先更新原子需求和追踪矩阵，再修改设计正文。
- 设计版本与需求版本分别维护，不能用设计版本替代需求基线。
- 代码核验发现设计事实错误时，修正 `AS-IS` 和受影响决策，并记录影响范围。
- 只修改受影响章节，避免重写整个文档造成无关差异。
- 已实现后的设计修订必须注明是“设计变更”还是“现状回填”。

## 9. 可复用生成提示词

以下提示词可用于后续需求生成设计。使用时替换尖括号内容：

```text
请基于 <需求文档路径及版本> 生成一份执行级技术设计文档，输出到 <设计文档路径>。

开始前：
1. 完整读取仓库 AGENTS.md、需求文档，以及需求明确引用的规范。
2. 记录当前分支/提交和工作区状态，不覆盖用户已有改动。
3. 按“仓库约束 > 需求 > 已批准规范 > 当前代码 > 补充文档 > 历史资料”处理信息；冲突不得静默解决。
4. 实际检查相关调用链、类、函数、SQL、服务配置和构建脚本，不得凭文件名或历史实现推测。

设计文档必须包含：
- 目标、范围内、范围外、输入基线和冲突处理；
- 原子化需求及稳定需求 ID；
- 当前实现、复用能力和差距；
- 接口、状态机、字段来源、可信上下文、审计、事务、并发和错误设计；
- 精确到文件和符号的修改清单、处理顺序及保持不变项；
- 配置、构建、环境前提、验证顺序和预期结果；
- “需求 ID -> 设计章节 -> 代码/配置落点 -> 验证方式”的追踪矩阵；
- 风险、假设、TBD 和明确不修改项。

规则：
- 不新增需求未授权的功能、抽象、依赖、字段或服务。
- 复用结论必须有当前代码证据。
- 代码片段只保留消除歧义所需的最小部分。
- 无法确认的内容标记 ASSUMPTION 或 TBD，不得伪装为事实。
- 生成后执行正向与反向追踪检查，并给出质量门禁结果。
- 本阶段只生成设计文档，不修改生产代码、测试或部署配置。
```

## 10. 完成定义

一份设计文档只有同时满足以下条件才算完成：

1. 完整覆盖需求，并能逐条追溯。
2. 与当前代码和配置可对接，不依赖未经验证的能力。
3. 修改范围、处理顺序、数据和异常语义足够明确。
4. 有可执行的验证方案和明确预期结果。
5. 无未说明的假设、无需求外设计、无阻塞性待确认项。

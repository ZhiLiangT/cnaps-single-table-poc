# CNAPS 凭证审核功能需求文档

> 文档版本：v1.0  
> 编写日期：2026-07-15  
> 需求状态：待评审  
> 适用项目：CNAPS 单表 POC  
> 接口基线：`docs/cnaps-frontend-api.md` v0.5（以当前工作区内容为准）

## 1. 文档目的

本文档定义 CNAPS 往账凭证单级审核功能的业务范围、状态流转、页面交互、异常处理、验收标准和上线约束，作为产品确认、开发、测试和部署验收的共同依据。

本项目的 HTTP API 使用“复核”命名，例如 `review-list`、`review-pass` 和 `review-return`；面向用户的页面统一使用“审核”文案。本文中的“审核”和 API 中的“复核”指同一业务动作。

## 2. 背景与现状

凭证创建和修改后进入 `10_PENDING_REVIEW` 状态，需要由操作员在审核列表中执行“审核通过”或“审核退回”。当前 API 文档已经定义了待审核查询、审核通过、审核退回以及完整状态机，但当前代码基线尚未形成可用的端到端审核功能：

- 凭证创建和修改已经能够产生 `10_PENDING_REVIEW` 状态。
- `10_PENDING_REVIEW`、`20_REVIEW_APPROVED`、`30_REVIEW_REJECTED`、`40_DELETED` 状态及历史 `00_DRAFT` 迁移脚本已经存在。
- 当前 WebFE Servlet 对审核列表、审核通过和审核退回请求返回 HTTP 405。
- 当前页面没有审核入口和审核列表，查询结果仍以原始 JSON 展示。
- 当前 WebFE 映射、Mock 客户端、Jolt 元数据、Tuxedo 服务注册和原生 C 审核服务尚未接通。

因此本需求不是单纯增加两个前端按钮，而是恢复并完成从 JSP 页面到 Oracle 数据库的完整单级审核链路。

## 3. 目标与成功标准

### 3.1 业务目标

1. 操作员能够查询当前机构的待审核凭证。
2. 列表能够清晰展示每张凭证的当前状态。
3. 操作员能够查看凭证详情后执行审核通过或审核退回。
4. 审核动作必须遵守状态流转规则，并能正确处理重复提交和并发状态变化。
5. 审核结果能够在通用凭证查询列表中被准确展示。

### 3.2 技术成功标准

1. Mock 模式和真实 Jolt/Tuxedo/Oracle 模式行为一致。
2. `mvn -f web-fe/pom.xml clean package` 测试通过并生成 WAR。
3. Tuxedo C 服务能够编译，并在 TUXCONFIG 和 Jolt metadata 中正确注册。
4. 完整部署脚本执行成功，健康检查中 `webfe`、`tuxedo`、`oracle` 均为 `UP`。
5. 端到端冒烟测试覆盖创建、待审核查询、审核通过、审核退回、退回后修改和最终状态查询。

## 4. 范围

### 4.1 本期范围

- 新增“审核处理”页面和全站审核导航入口。
- 待审核凭证分页查询。
- 工作日期范围、流水号查询条件。
- 列表状态信息展示。
- 凭证详情查看。
- 单笔审核通过。
- 单笔审核退回。
- 审核成功后的列表刷新和通用查询状态展示。
- 并发状态变化、网络失败、服务异常和空数据等反馈。
- Mock、WebFE、Jolt、Tuxedo C、Oracle 全链路支持。
- 自动化测试、冒烟测试和部署验证。

### 4.2 本期不包含

- 登录、账号、角色和权限管理。
- 经办员与审核员分离控制。
- “审核员不得审核本人录入凭证”的限制。
- 审核意见、退回原因或删除原因输入。
- 批量审核、全选审核或批量退回。
- 二级或多级审核。
- 消息通知、待办提醒或外部工作流集成。
- 真实扣账、CNAPS 报文发送或外联系统调用。
- 已审核凭证的撤销审核、反审核或状态回退。

上述限制与 `cnaps-frontend-api.md` 的当前 POC 契约一致。若后续增加退回原因、人员分离或多级审核，必须先变更 API、数据模型和本需求文档，不能只在页面增加字段。

## 5. 用户与权限

### 5.1 用户角色

当前 POC 仅定义一个泛化的“操作员”角色。操作员编号和机构号由服务端配置提供，浏览器不得传入或覆盖：

- `operatorNo`：由 WebFE 运行配置固定。
- `branchNo`：由 WebFE 运行配置固定。

### 5.2 权限规则

- 页面不做登录态校验。
- 页面不根据角色隐藏审核入口。
- 服务端不校验审核人与录入人是否相同。
- 所有状态合法性必须由服务端最终校验，前端按钮控制只用于改善交互，不能作为业务安全边界。

## 6. 业务状态模型

### 6.1 状态定义

| 状态码 | 页面文案 | 展示语义 | 允许操作 |
| --- | --- | --- | --- |
| `10_PENDING_REVIEW` | 待审核 | 凭证已录入或退回后已修改，等待审核 | 修改、删除、审核通过、审核退回 |
| `20_REVIEW_APPROVED` | 审核通过 | 审核完成，不允许再次修改或审核 | 查询、查看详情 |
| `30_REVIEW_REJECTED` | 审核退回 | 审核未通过，等待经办修改或删除 | 修改、删除 |
| `40_DELETED` | 已删除 | 凭证已逻辑删除 | 查看详情；通用查询中显式包含删除记录后查询 |

未知状态不得被映射成任一已知状态。页面应显示“未知状态（原始状态码）”，并隐藏审核按钮，以免错误操作。

### 6.2 状态流转

```text
创建凭证
  -> 10_PENDING_REVIEW

10_PENDING_REVIEW
  -> 审核通过 -> 20_REVIEW_APPROVED
  -> 审核退回 -> 30_REVIEW_REJECTED
  -> 删除     -> 40_DELETED

30_REVIEW_REJECTED
  -> 修改     -> 10_PENDING_REVIEW
  -> 删除     -> 40_DELETED
```

### 6.3 审核规则

1. 只有服务端当前状态为 `10_PENDING_REVIEW` 的凭证可以执行审核。
2. 审核通过后状态必须变为 `20_REVIEW_APPROVED`。
3. 审核退回后状态必须变为 `30_REVIEW_REJECTED`。
4. 审核动作成功时 `versionNo` 必须加 1。
5. 审核动作成功时必须更新 `checkerNo`、`checkerTime`、`lastAction`、`lastOperatorNo`、`lastRequestId`、`lastActionTime` 和 `updatedAt`。
6. 审核通过的 `lastAction` 为 `REVIEW_PASS`；审核退回的 `lastAction` 为 `REVIEW_RETURN`。
7. 当前 API 不接收审核意见和退回原因，审核请求不得构造虚构的默认原因。
8. 页面操作完成后必须重新从服务端读取列表或详情，不允许仅通过前端本地修改状态来假定成功。

## 7. 页面与导航需求

### 7.1 全局导航

首页、录入页、查询页和审核页的顶部导航统一包含：

- 首页
- 录入
- 查询
- 审核

当前页面对应的导航项应有可识别的选中状态，并通过 `aria-current="page"` 标识。

### 7.2 审核处理页面

新增 `cnaps-review.jsp`，页面标题为“CNAPS 凭证审核”，主标题为“审核处理”。页面由以下区域组成：

1. 查询条件区。
2. 查询结果摘要区。
3. 待审核凭证表格。
4. 分页区。
5. 凭证详情区。
6. 全局消息提示区。

页面首次打开时默认查询第 1 页，每页 10 条，不默认限制工作日期。

### 7.3 通用查询页面

现有 `cnaps-query.jsp` 的查询结果应由原始 JSON 改为结构化表格，至少展示 API 列表记录中的全部字段，并将状态显示为中文状态标签。通用查询页不提供审核按钮，避免查询职责和审核职责混杂；用户需要审核时通过导航进入审核页。

调试用原始 JSON 如需保留，只能放在默认折叠的“接口响应详情”区域，不得作为主要业务列表。

## 8. 待审核列表需求

### 8.1 查询条件

| 条件 | 控件 | 规则 |
| --- | --- | --- |
| 开始工作日期 | `date` 输入框 | 可空；格式 `yyyy-MM-dd`；包含该日 |
| 结束工作日期 | `date` 输入框 | 可空；格式 `yyyy-MM-dd`；包含该日 |
| 流水号 | 文本输入框 | 可空；精确匹配；提交前去除首尾空白 |
| 每页条数 | 下拉框 | 允许 10、20、50、100；默认 10 |

查询和重置按钮规则：

- 点击“查询”后页码重置为 1。
- 开始日期晚于结束日期时，浏览器端立即提示，不发起请求。
- 点击“重置”清空日期和流水号，恢复每页 10 条，并重新查询第 1 页。
- 空条件请求体为 `{"pageNo":1,"pageSize":10}`，不得发送 `workDate`。

### 8.2 列表字段

审核列表按以下顺序展示：

| 列 | API 字段 | 展示规则 |
| --- | --- | --- |
| 凭证编号 | `billId` | 完整值；可复制；同时作为查看详情入口 |
| 工作日期 | `workDate` | `yyyy-MM-dd` |
| 流水号 | `serialNo` | 原样展示 |
| 凭证号 | `voucherNo` | 为空显示 `—` |
| 收款账号 | `payeeAccountNo` | 原样展示；为空显示 `—` |
| 收款人 | `payeeName` | 原样展示；为空显示 `—` |
| 金额 | `amount` | 两位小数、右对齐；不使用浮点数重新计算 |
| 当前状态 | `status` | 中文标签和原始状态码；待审核列表正常情况下为 `10_PENDING_REVIEW` |
| 操作 | 无 | 查看详情、审核通过、审核退回 |

### 8.3 列表状态

- 加载中：显示明确的加载提示，禁用查询和分页的重复提交。
- 空数据：显示“暂无待审核凭证”，不得显示空白表格或错误提示。
- 加载失败：保留当前查询条件，显示服务端 `respMsg`；允许用户重试。
- 查询成功：显示“共 N 条，第 X/Y 页”。当 `total=0` 时总页数按 0 展示。
- 最后一页最后一条被审核后，如果当前页变为空且 `pageNo>1`，自动查询前一页。

### 8.4 分页规则

- 上一页在第 1 页禁用。
- 下一页在 `pageNo * pageSize >= total` 时禁用。
- 翻页请求保留当前查询条件。
- 服务端返回的 `pageNo`、`pageSize` 和 `total` 是页面状态的唯一可信来源。

## 9. 凭证详情需求

点击“查看详情”或凭证编号时，调用 `GET /api/cnaps/vouchers/{billId}` 并在详情面板中展示完整凭证字段。详情至少分组展示：

- 基本信息：凭证编号、工作日期、流水号、凭证号、业务类型、状态。
- 付款信息：付款账号三段、付款账户户名、付款人名称、地址、开户行。
- 收款信息：收款账号、收款人名称、地址、接收行号和行名。
- 金额与渠道：金额、手续费、优先级、系统类型、扣款方式、收费方式、发送方式、传真标识。
- 附加信息：备注。
- 审计信息：录入操作员、机构号、审核员、审核时间、最后动作、最后操作员、最后动作时间、创建时间、更新时间、版本号。

当前 API 文档未公开 `reviewComment`、`rejectReason` 和 `deleteReason`，页面不得依赖或展示这三个字段。

详情加载过程中不得阻塞列表浏览；详情加载失败时只关闭或标记详情区，不清空已加载列表。

## 10. 审核通过需求

### 10.1 入口条件

- 仅当列表记录状态为 `10_PENDING_REVIEW` 时展示并启用“审核通过”。
- 最终合法性由服务端再次校验。

### 10.2 用户流程

1. 用户点击“审核通过”。
2. 页面弹出确认提示，至少包含凭证编号、收款人和金额。
3. 用户取消时不发送请求。
4. 用户确认后，页面仅禁用该凭证行的审核按钮，并显示处理中状态。
5. 页面调用 `POST /api/cnaps/vouchers/{billId}/review-pass`，不传请求体。
6. `respCode=0000` 时提示“审核通过成功”，然后重新查询当前审核列表。
7. 若详情面板正在展示该凭证，则重新获取详情或关闭详情面板，不能继续显示旧状态。

### 10.3 结果

- 数据库状态为 `20_REVIEW_APPROVED`。
- 该凭证从待审核列表消失。
- 在通用查询中按 `20_REVIEW_APPROVED` 查询能够找到该凭证并显示“审核通过”。

## 11. 审核退回需求

### 11.1 入口条件

- 仅当列表记录状态为 `10_PENDING_REVIEW` 时展示并启用“审核退回”。
- 本期不输入退回原因。

### 11.2 用户流程

1. 用户点击“审核退回”。
2. 页面弹出确认提示，明确说明退回后凭证需要修改并重新提交审核。
3. 用户取消时不发送请求。
4. 用户确认后，页面仅禁用该凭证行的审核按钮，并显示处理中状态。
5. 页面调用 `POST /api/cnaps/vouchers/{billId}/review-return`，不传请求体。
6. `respCode=0000` 时提示“审核退回成功”，然后重新查询当前审核列表。

### 11.3 结果

- 数据库状态为 `30_REVIEW_REJECTED`。
- 该凭证从待审核列表消失。
- 在通用查询中按 `30_REVIEW_REJECTED` 查询能够找到该凭证并显示“审核退回”。
- 该凭证后续允许修改或删除；修改后重新进入 `10_PENDING_REVIEW`。

## 12. 接口需求

### 12.1 待审核查询

```http
POST /api/cnaps/vouchers/review-list
Content-Type: application/json; charset=UTF-8
```

请求示例：

```json
{
  "startWorkDate": "2026-07-01",
  "endWorkDate": "2026-07-15",
  "serialNo": "0002000",
  "pageNo": 1,
  "pageSize": 10
}
```

空筛选条件允许只传分页参数。接口必须强制只返回 `10_PENDING_REVIEW`，不得接受客户端传入的其他状态覆盖该条件。

成功响应示例：

```json
{
  "respCode": "0000",
  "respMsg": "查询成功",
  "data": {
    "pageNo": 1,
    "pageSize": 10,
    "total": 1,
    "records": [
      {
        "billId": "B202607157720002000",
        "workDate": "2026-07-15",
        "serialNo": "0002000",
        "voucherNo": "PZ202607150001",
        "payeeAccountNo": "622200000000000001",
        "payeeName": "测试收款人",
        "amount": "5600.00",
        "status": "10_PENDING_REVIEW",
        "versionNo": 1
      }
    ]
  }
}
```

### 12.2 审核通过

```http
POST /api/cnaps/vouchers/{billId}/review-pass
```

- 无请求体。
- 仅 `10_PENDING_REVIEW` 可操作。
- 成功后状态为 `20_REVIEW_APPROVED`。

### 12.3 审核退回

```http
POST /api/cnaps/vouchers/{billId}/review-return
```

- 无请求体。
- 仅 `10_PENDING_REVIEW` 可操作。
- 成功后状态为 `30_REVIEW_REJECTED`。

### 12.4 凭证详情

```http
GET /api/cnaps/vouchers/{billId}
```

用于审核前查看完整业务信息以及操作后获取服务端最终状态。

### 12.5 通用查询

```http
POST /api/cnaps/vouchers/query
Content-Type: application/json; charset=UTF-8
```

通用查询列表必须展示每条记录的 `status`。查询已删除记录时，客户端必须显式传 `includeDeleted=true`。

## 13. 错误与并发处理

| 场景 | HTTP / `respCode` | 页面行为 |
| --- | --- | --- |
| 请求成功 | 200 / `0000` | 显示成功消息并刷新服务端数据 |
| 必填字段或请求格式错误 | 400 / `2001`、`2002`、`2003` | 显示 `respMsg`，保留条件，不自动重试 |
| 凭证不存在 | 404 / `3001` | 提示凭证不存在或已不可见，刷新列表 |
| 当前状态不允许操作 | 409 / `3003` | 提示状态不允许，刷新列表和详情 |
| 审核时状态已变化 | 409 / `3004` | 提示“凭证状态已被其他操作更新”，刷新列表，不继续重试当前动作 |
| 数据库错误 | 500 / `4001` | 提示系统繁忙，保留查询条件，允许手工重试 |
| Tuxedo 超时 | 504 / `4002` | 明确提示结果可能未知；先刷新详情或列表确认最终状态，不自动重复审核 |
| 后端不可用 | 503 / `4003` | 提示服务不可用，允许手工重试查询 |
| 未分类错误 | 500 / `9999` | 显示通用错误和服务端消息 |
| 网络错误或非 JSON 响应 | 无统一业务码 | 显示网络/响应异常；不得把操作标记为成功 |

审核动作具有业务副作用。发生超时、断网或非 JSON 响应时，前端不得自动再次提交审核请求，必须通过重新查询确认状态，避免重复操作。

## 14. 非功能需求

### 14.1 可用性

- 所有主要操作都有加载、成功、失败和空数据状态。
- 审核按钮必须有明确且不同的视觉语义；退回按钮不得与通过按钮使用相同颜色。
- 金额右对齐，状态标签在列表滚动时仍易识别。
- 宽度不足时表格允许水平滚动，不得截断操作按钮。

### 14.2 可访问性

- 所有输入框必须具有关联的 `<label>`。
- 按钮使用原生 `<button>`，不得用仅可点击的 `<div>`。
- 加载和操作结果区域使用 `aria-live="polite"`。
- 颜色不能是状态识别的唯一手段，状态必须同时显示文字。
- 对话框打开后应聚焦到对话框，关闭后焦点返回触发按钮。

### 14.3 安全性

- 服务端返回的文本必须通过 `textContent` 或 DOM 文本节点渲染，不得直接拼接到 `innerHTML`。
- `billId` 放入 URL 前必须使用 `encodeURIComponent`。
- 浏览器不得提交 `operatorNo`、`branchNo`、状态目标值或服务端审计字段。
- 后端不得信任前端按钮状态，必须重新检查数据库当前状态。

### 14.4 兼容性

- 不引入新的前端构建工具或第三方框架。
- 保持 Java 17、Servlet 4.0、JSP 2.3 和现有 Maven WAR 打包方式。
- 保持 Tomcat 上下文路径可配置，前端 API 地址不得写死为域名或 `/` 根路径。

### 14.5 性能与容量

- 默认每页 10 条，单页最大 100 条，与原生查询服务上限保持一致。
- 页面不得为每条列表记录自动请求详情；详情仅在用户主动查看时加载。
- 同一查询只允许一个进行中的列表请求；新查询发起时应使旧响应失效，避免后返回的旧请求覆盖新结果。

## 15. 验收标准

### 15.1 列表与状态展示

1. 给定存在待审核凭证，打开审核页时，列表展示凭证编号、工作日期、流水号、凭证号、收款账号、收款人、金额、当前状态和操作按钮。
2. 待审核状态显示为“待审核”，同时能够查看原始状态码 `10_PENDING_REVIEW`。
3. 通用查询分别按四个状态查询时，页面展示正确的中文状态文案。
4. 服务端返回未知状态时，页面显示未知状态和原始值，且不出现审核按钮。

### 15.2 审核通过

1. 创建一张凭证后可在审核列表找到。
2. 确认审核通过后接口返回 `0000`，记录从审核列表消失。
3. 通用查询按 `20_REVIEW_APPROVED` 能找到该记录。
4. 详情显示 `checkerNo`、`checkerTime`、`lastAction=REVIEW_PASS` 且 `versionNo` 增加 1。
5. 对同一记录再次调用审核通过返回 `3004`，状态保持不变。

### 15.3 审核退回

1. 确认审核退回后接口返回 `0000`，记录从审核列表消失。
2. 通用查询按 `30_REVIEW_REJECTED` 能找到该记录。
3. 详情显示 `lastAction=REVIEW_RETURN` 且 `versionNo` 增加 1。
4. 退回记录能够修改；修改后状态回到 `10_PENDING_REVIEW`，再次出现在审核列表。

### 15.4 并发与异常

1. 两个客户端同时对同一待审核凭证执行不同审核动作时，只允许一个成功，另一个返回 `3004`。
2. 收到 `3004` 后页面刷新并展示服务端最终状态，不重复提交。
3. 日期范围非法时浏览器端不发请求，服务端直接调用也返回 `2002`。
4. Tuxedo 不可用时页面显示错误，不把凭证移出本地列表作为成功结果。

### 15.5 编译与部署

1. WebFE Maven 单元及契约测试全部通过。
2. C 服务编译无新增警告或链接错误。
3. Tuxedo 状态中可见 `CNAPS5702Q`、`CNAPS5702A`、`CNAPS5702R`。
4. Jolt metadata 加载后 WebFE 能调用三个服务。
5. 完整部署和健康检查成功。
6. 生产式 Jolt 模式冒烟测试通过完整审核生命周期。

## 17. 上线与数据要求

1. 新增审核接口不要求新增数据库列，复用现有状态、审核和审计字段。
2. 上线前必须确认历史 `00_DRAFT` 已通过 `scripts/migrate-voucher-review.sh` 迁移为 `10_PENDING_REVIEW`。
3. 状态迁移只能在 Tomcat 和 Tuxedo 停止的维护窗口执行；迁移失败不得启动新版本。
4. 不能用 `scripts/init-db.sh` 替代升级迁移，避免破坏已有数据。
5. Jolt metadata 和 TUXCONFIG 必须随 C 服务及 WAR 一起发布，不能只替换 WAR。
6. 回滚应用前应确认新状态数据仍能被回滚版本识别；当前已退役的 `00_DRAFT` 不允许重新写入。

## 18. 假设与待确认项

以下决定依据当前 API 文档，可直接作为第一期开发默认值，不阻塞开发：

1. 审核退回不填写退回原因；两个审核接口均无请求体。
2. 当前 POC 不区分经办员和审核员，允许服务端固定操作员审核其本人录入的凭证。
3. 本期只支持单笔、单级审核。
4. 审核页只展示待审核记录；全部状态在通用查询页查看。
5. 审核列表默认不限制工作日期，遵循 API 的空日期范围语义。

如业务方希望“退回原因必填”“审核员与经办员必须分离”“审核页默认只查当天”或“支持批量审核”，需在开发前明确，因为这些变化会修改 API 契约、页面流程、测试用例，部分变化还会影响身份体系和数据库设计。

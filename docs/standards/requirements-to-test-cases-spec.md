# 需求文档生成手动测试用例规范

> 版本：v1.1（手动测试用例版）
> 适用范围：CNAPS Single-Table POC 及结构相近后端系统的手动功能测试
> 示例输入：`docs/requirements/cnaps-review-requirements.md`
> 示例输出：`docs/test-cases/cnaps-review-test-cases.md`

## 1. 目的

本规范用于把需求文档稳定地转换为可由测试人员逐步执行、可追溯、可复查、可维护的手动测试用例。标准化过程需要保证：

- 每条已确认需求至少有一个测试用例，每个测试用例都有明确来源。
- 正常、异常、边界、状态、权限/可信上下文、并发和故障路径不会因经验差异被遗漏。
- 前置条件、输入、步骤和预期结果足够明确，不依赖执行人员再次猜测。
- 需求不完整或输入冲突时显式形成 TBD，不把假设伪装成产品预期。
- 需求变更后可以快速定位受影响用例、测试数据、执行步骤和回归范围。

本规范约束“手动测试用例设计与执行准备”，不替代实际执行、缺陷管理或发布审批。自动化测试可在手动用例稳定后另行建设，不是本流程的交付物。

## 2. 基本原则

1. **先验证需求可测，再生成用例。** 无唯一预期的需求不能直接生成通过/失败判定。
2. **先原子化，再做覆盖。** 一条需求只描述一个可观察结果，并使用稳定 ID。
3. **以用户可操作和测试人员可观察的行为为主。** 优先通过 API、数据库查询、日志和配置检查验收；内部实现约束作为人工检查项，不要求编写测试代码。
4. **同时验证改变和未改变。** 写操作既检查目标字段，也检查禁止改变的记录、版本和审计字段。
5. **错误结果必须精确。** 至少断言 HTTP 状态、业务码、响应数据和持久化状态。
6. **测试用例独立。** 每个破坏性用例使用独立数据，或提供测试人员可重复执行的数据重置步骤。
7. **不追求用例数量，追求风险与规则覆盖。** 能用参数化或决策表表达的组合不机械复制。

## 3. 输入、优先级与基线

### 3.1 必需输入

| 输入 | 必需 | 记录内容 |
| --- | :---: | --- |
| 仓库/任务约束 | 是 | 允许范围、禁止项、真实验证环境、不可修改项 |
| 需求文档 | 是 | 路径、版本、日期、状态 |
| 已批准设计 | 条件必需 | 与需求冲突时的设计决策、调用链、事务和并发方案 |
| API/数据规范 | 条件必需 | 字段、类型、错误码、响应信封、数据库语义 |
| 当前实现 | 是 | 现有行为、手动入口、可观察点和日志/数据库查询方式 |
| 测试环境能力 | 是 | 真实依赖、手动操作工具、数据准备和故障注入能力 |
| 变更基线 | 是 | 分支/提交、工作区状态、相关服务版本 |

### 3.2 信息优先级

默认按以下顺序处理：

```text
仓库和任务约束
> 已批准需求
> 已批准设计/领域规范
> 专项 API 或数据规范
> 当前代码和配置事实
> 历史资料、示例和口头说明
```

高优先级输入定义“应该是什么”，当前实现说明“现在是什么”。二者不一致时，应形成缺陷候选或待确认项，不能静默把现状写成预期。

测试用例文档头必须记录所有实际使用的输入版本。需求或设计没有版本时，记录文件提交哈希或内容哈希。

## 4. 信息分类与可测性审查

### 4.1 信息标签

| 标签 | 含义 | 处理方式 |
| --- | --- | --- |
| `REQ` | 需求明确规定的行为 | 必须生成覆盖用例 |
| `CONSTRAINT` | 范围、架构、兼容性或禁止项 | 转为人工检查项或非回归断言 |
| `CONTRACT` | API、字段、状态、错误码或数据契约 | 生成精确契约断言 |
| `AS-IS` | 从当前实现核验的事实 | 用于确定手动操作路径、证据来源和准备数据，不得覆盖需求 |
| `RISK` | 高损失或高概率失败点 | 提升优先级或增加组合覆盖 |
| `ASSUMPTION` | 暂时采用但未被证明的假设 | 写明依据、责任人和失效影响 |
| `TBD` | 无法得到唯一预期的问题 | 阻止相关用例进入可执行状态 |

### 4.2 可测性检查清单

对每条需求确认：

- 触发条件是否明确：角色/上下文、当前状态、请求和数据。
- 处理规则是否明确：默认值、覆盖顺序、计算、过滤和状态转换。
- 成功结果是否可观察：响应、数据库、消息、日志或外部副作用。
- 失败结果是否明确：业务码、HTTP 状态、回滚和不变项。
- 边界是否明确：长度、范围、日期、精度、空值和最大容量。
- 并发语义是否明确：锁、版本、幂等、重复请求和胜者结果。
- 时间和审计来源是否明确：应用、数据库或外部系统。
- 范围外行为是否明确：拒绝、忽略、兼容还是未定义。

任一关键项缺失时建立 TBD。TBD 至少包含问题、冲突证据、建议选项、影响用例和确认责任方。

## 5. 标准生成流程

### 5.1 阶段一：固定范围与风险

1. 记录输入版本、代码基线和环境基线。
2. 提取目标、范围内、范围外、完成标准和禁止项。
3. 识别资金、数据一致性、安全、并发、审计和兼容性风险。
4. 标明真实依赖与 Mock 差异，确定哪些结果必须在集成环境验证。

阶段产物：基线清单、范围清单、风险清单。

### 5.2 阶段二：需求原子化

把复合语句拆成单一、可验证的原子要求。推荐编号：

```text
<功能>-API-001  接口和响应契约
<功能>-FUN-001  功能行为
<功能>-VAL-001  输入校验和边界
<功能>-STA-001  状态和业务规则
<功能>-DAT-001  数据与审计
<功能>-SEC-001  权限或可信上下文
<功能>-CON-001  并发、幂等和一致性
<功能>-ERR-001  错误与恢复
<功能>-NFR-001  性能、容量和可靠性
<功能>-SCP-001  范围或实现约束
```

每条原子要求必须包含：需求 ID、规范化描述、来源章节、优先级、风险、可观察结果和状态（已确认/TBD）。

错误示例：“校验状态并更新审计字段后返回摘要。”

正确拆分：状态前置条件、目标状态、每个审计字段来源、版本规则、响应字段集合。

### 5.3 阶段三：建立测试模型

根据需求选择模型，不要求所有需求使用同一种方法：

| 模型/技术 | 适用场景 | 最低输出 |
| --- | --- | --- |
| 等价类 | 字段类型、格式、合法/非法集合 | 每个有效和无效类至少一个代表值 |
| 边界值 | 数值、长度、日期、分页、金额 | `min-1/min/min+1/max-1/max/max+1` 中适用值 |
| 决策表 | 多条件共同决定结果 | 每条有效规则和关键无效组合 |
| 状态转换 | 审批、订单、生命周期 | 合法边、非法边、重复动作和闭环 |
| 场景法 | 跨接口业务闭环 | 主流程、替代流、中断后恢复 |
| CRUD/数据流 | 字段持久化和映射 | 输入、存储、输出及不可变字段 |
| 错误推测 | 解析、路由、集成边界 | 空值、重复值、未知值、超时和部分失败 |
| 并发模型 | 乐观锁、抢占、幂等 | 同动作、相反动作、版本变化和胜者审计 |
| 故障注入 | 事务、外部服务、消息 | 每个失败点的错误码、回滚和重试语义 |
| 人工结构检查 | 服务注册、元数据、禁止项 | 使用只读命令核对唯一性、存在性、不存在性和原内容保持 |

状态型需求必须先画状态表，再写用例：

| 当前状态 | 动作 | 目标状态/错误 | 数据变化 | 是否允许 |
| --- | --- | --- | --- | :---: |
| `<S1>` | `<A1>` | `<S2>` | `<字段变化>` | 是 |
| `<S2>` | `<A1>` | `<错误码>` | 无变化 | 否 |

### 5.4 阶段四：形成测试点清单

按以下维度扫描每条原子要求：

```text
入口/路由
→ 请求字段与可信上下文
→ 校验、默认和覆盖规则
→ 业务/状态处理
→ 数据、审计和事务
→ 响应字段与错误映射
→ 重复、并发和故障
→ 范围约束与兼容性
```

测试点是“需要验证的事实”，不是操作步骤。例如：“客户端 status 被服务端待审核状态覆盖”是测试点；“调用接口看看结果”不是。

### 5.5 阶段五：设计数据和前置条件

先设计数据角色，再填实际值：

- 每个有效状态至少一条独立记录。
- 每个边界点的数据仅改变一个变量。
- 机构、租户、用户隔离至少准备本域和域外数据。
- 并发用例为每轮准备新记录，保存初始版本。
- 写操作保存数据库前快照，并定义清理或重置方式。
- 时间断言使用窗口，不依赖不同主机时钟完全相等。
- ID 由系统生成时，在准备阶段捕获并传递，避免硬编码。

测试数据不得包含真实客户隐私或生产凭证。

### 5.6 阶段六：编写测试用例

每个用例只验证一个主要意图，但可以包含为证明该意图所必需的多层断言。步骤应由不了解实现细节的测试人员按文档独立完成。用例 ID 一经引用不得复用；需求变更导致用例废弃时保留 ID 并标记“已废弃”。

推荐格式：

| 字段 | 必需 | 编写要求 |
| --- | :---: | --- |
| 用例 ID | 是 | 稳定、唯一，如 `PAY-TC-CON-001` |
| 标题 | 是 | 条件 + 动作 + 结果，不写“验证功能” |
| 需求 ID | 是 | 一个或多个原子需求 ID |
| 优先级 | 是 | P0/P1/P2，基于风险而非作者偏好 |
| 执行方式/工具 | 是 | Postman、curl、SQL 客户端、日志查询、双终端并发或人工代码检查 |
| 执行状态 | 是 | 未执行/通过/失败/阻塞/不适用；阻塞必须写原因 |
| 前置条件 | 是 | 环境、上下文、状态、初始版本和依赖 |
| 测试数据 | 是 | 明确值或数据 ID，禁止“任意合法值” |
| 步骤 | 是 | 编号、可重复、顺序明确；写清输入位置、请求方式和查询动作 |
| 预期结果 | 是 | 按步骤编号对应，包含界面/API 响应、数据变化和不变项 |
| 清理 | 条件必需 | 恢复数据和服务的方法 |
| 证据 | 执行时必需 | 请求/响应、日志、SQL 快照、截图或报告链接 |
| 实际结果 | 执行时必需 | 记录实际值，禁止只填“同预期” |
| 缺陷 ID | 条件必需 | 失败时关联缺陷；阻塞时关联环境问题或确认项 |

#### 5.6.1 手动用例示例

| 字段 | 示例内容 |
| --- | --- |
| 用例 ID / 标题 | `REV-TC-ACT-001` / 待审核凭证审核通过 |
| 需求 ID | `REV-STA-001`、`REV-AUD-003` |
| 优先级 / 状态 | P0 / 未执行 |
| 执行工具 | Postman、Oracle SQL 客户端、Tuxedo 服务日志 |
| 前置条件 | 凭证 `BILL-001` 为 `10_PENDING_REVIEW`；版本为 3；已保存审计字段快照 |
| 测试数据 | URL 中 `billId=BILL-001`；请求无 Body |
| 操作步骤 | 1. 记录开始时间 `T0`。<br>2. POST `/api/cnaps/vouchers/BILL-001/review-pass`。<br>3. 记录结束时间 `T1`。<br>4. 保存响应。<br>5. 查询该凭证数据库记录。 |
| 预期结果 | HTTP 200、`respCode=0000`；状态为 `20_REVIEW_APPROVED`；`lastAction=REVIEW_PASS`；版本为 4；审核时间位于 `[T0,T1]`；其他凭证无变化 |
| 证据 | Postman 请求/响应、操作前后 SQL 结果、服务日志和时间记录 |
| 清理 | 该用例数据不复用；按测试环境清理清单删除或标记本次数据 |

示例中的 ID、版本和时间都可直接比较；没有使用“正常”“正确”或“任意待审核凭证”等需要执行人员二次猜测的表达。

### 5.7 阶段七：覆盖与反向审查

建立双向追踪矩阵：

| 需求 ID | 风险 | 测试点 | 用例 ID | 手动执行方式 | 状态 |
| --- | --- | --- | --- | --- | --- |
| `ABC-STA-001` | 高 | 合法转换、重复动作 | `ABC-TC-001/002` | API + SQL 核验 | 可执行 |

执行两种检查：

- 正向追踪：每条已确认需求是否有测试点和用例。
- 反向追踪：每个用例是否有需求或风险来源，是否测试了未授权功能。

覆盖率按“已确认需求”计算：

```text
需求覆盖率 = 有至少一个可执行手动用例的已确认需求数 / 已确认需求总数
用例就绪率 = 前置、数据、步骤、预期和清理均完整的用例数 / 已设计用例总数
状态转换覆盖率 = 已覆盖的合法和非法状态边数 / 要求覆盖的状态边总数
错误映射覆盖率 = 已覆盖的错误码与 HTTP 组合数 / 已定义组合总数
```

TBD 不得从分母中静默删除；必须在报告中单独列出数量、风险和负责人。

### 5.8 阶段八：评审、批准与维护

至少由需求负责人和测试负责人评审；涉及事务、并发、安全或数据库时增加相应技术负责人。评审结论分为：通过、带条件通过、待确认、拒绝。

需求变化时先做影响分析，再更新用例：

1. 更新原子需求及版本。
2. 从追踪矩阵找到受影响测试点和用例。
3. 更新测试数据、手动步骤、预期结果、证据要求和清理方式。
4. 标记新增、修改、废弃用例，不重用旧 ID。
5. 重跑受影响用例及相关回归集。

## 6. 预期结果编写标准

预期结果必须可观察、可比较、可判定。禁止只写“成功”“失败”“正常返回”“数据正确”。

### 6.1 API 结果

至少写明：

- HTTP 状态。
- 业务码和必要的错误语义。
- 顶层响应信封。
- `data` 的精确字段集合、类型、值或值域。
- 失败时 `data` 是否为 `null`。

### 6.2 数据库结果

写操作至少验证：

- 目标记录和目标状态。
- 版本增量，不只验证“版本变了”。
- 审计字段的值、来源和时间窗口。
- 未授权字段、其他记录和失败操作的数据不变。
- 事务失败没有部分提交。

### 6.3 并发结果

不得只写“一个成功一个失败”。至少写明：

- 各响应的准确组合和数量。
- 最终状态与胜者关系。
- 最终版本相对初始版本的增量。
- 审计字段只反映胜者。
- 建议重复轮数及每轮独立数据。

### 6.4 时间结果

优先断言来源、格式、非空、时区和操作时间窗口。只有单一数据库语句保证相同时间时，才能断言多个时间字段完全相等。

## 7. 手动执行方式与证据标准

| 测试内容 | 手动执行方式 | 必留证据 |
| --- | --- | --- |
| HTTP 请求、字段校验和响应信封 | Postman 或 curl 发送请求 | 完整请求、HTTP 状态和响应 Body |
| 状态、数据库、审计和版本 | API 操作前后使用只读 SQL 查询 | 操作前后 SQL、结果快照和请求时间窗口 |
| 机构或用户上下文 | 使用不同环境配置或输入伪造值 | 服务端配置、请求内容和最终审计值 |
| 并发乐观锁 | 两个终端或两个 Postman Runner 在约定时刻同时发送 | 双方开始时间、两个响应、最终 SQL 快照 |
| 超时、不可用和回滚 | 测试人员与环境管理员协作注入可恢复故障 | 故障起止时间、操作记录、响应和恢复确认 |
| 服务注册、元数据和禁止项 | 使用只读搜索命令或人工代码评审 | 命令、输出、代码基线和评审结论 |

手动验收必须尽量经过真实 WebFE、Jolt、Tuxedo 和 Oracle 链路。Mock 结果只能作为辅助证据，不能替代数据库事务、Oracle 时间、真实中间件或并发锁行为。

### 7.1 单条用例执行记录

每次执行至少记录：

```text
用例 ID：
执行环境/版本：
执行人：
执行时间：
测试数据 ID / billId：
实际步骤与输入：
实际响应：
数据库/日志证据：
结果：通过 / 失败 / 阻塞 / 不适用
缺陷或阻塞单号：
清理结果：
```

手动执行中临时改变步骤、数据或环境时，必须记录偏差；不得在执行完成后把实际操作倒写成原用例而不保留变更记录。

## 8. 优先级与退出规则

### 8.1 优先级

- `P0`：核心业务闭环、数据一致性、状态、版本、审计、安全、并发和回滚。
- `P1`：主要筛选、边界、错误映射、契约和服务不可用。
- `P2`：低风险兼容性、空结果、超出末页和人工结构检查。

### 8.2 手动测试用例设计完成定义

- [ ] 输入文档、代码和环境基线已记录。
- [ ] 所有复合需求已原子化并编号。
- [ ] 每条已确认需求至少有一个可由测试人员执行的手动用例。
- [ ] 每个用例都有需求或风险来源。
- [ ] 主流程、替代流、异常流和恢复流均已覆盖。
- [ ] 合法/非法状态转换、重复操作和并发竞争均已覆盖。
- [ ] 边界、默认值、空值、格式和越界值均有结论或 TBD。
- [ ] 成功和失败用例均包含数据库改变与不变断言。
- [ ] 错误码与 HTTP 状态逐一覆盖。
- [ ] 测试数据可重复准备、隔离和清理。
- [ ] 每个用例都写明执行工具、编号步骤、对应预期和证据要求。
- [ ] 执行状态、实际结果、缺陷和清理结果有统一记录位置。
- [ ] Mock 与真实集成环境的证据边界明确。
- [ ] 追踪矩阵完成正向和反向检查。
- [ ] 所有 TBD 有风险、影响、负责人和关闭条件。

关键契约存在未关闭 TBD 时，文档状态必须为“待确认”，不得写“手动测试用例设计完成”。

## 9. 评审门禁

出现以下任一问题，测试用例不得进入正式执行：

- 预期结果来自作者猜测，无法定位到需求、设计或规范。
- 用例依赖执行顺序或共享的不可重置数据。
- 只验证响应，不验证关键持久化结果或回滚。
- 并发用例没有同时起跑机制、初始版本或胜者审计断言。
- 用“任意值”“适当数据”“返回正常”等模糊描述。
- 测试要求修改生产逻辑或添加线上测试开关，且未获批准。
- 为追求覆盖率把 TBD 当成已确认需求，或静默排除高风险分支。

## 11. 可复用生成提示词

```text
请基于 <需求文档路径及版本> 生成一份供测试人员逐步执行的手动测试用例文档，输出到 <目标路径>。

开始前：
1. 完整读取仓库约束、需求文档及其明确引用的设计、API 和数据规范。
2. 记录代码基线、工作区状态、真实测试环境、手动操作工具、证据来源和 Mock 限制。
3. 按“仓库约束 > 已批准需求 > 已批准设计/领域规范 > API/数据规范 > 当前代码事实 > 历史资料”处理信息。
4. 需求与实现不一致时分别记录“期望”和“现状”，不得用现状静默覆盖需求。

生成过程：
1. 将需求拆成带稳定 ID 的原子、可验证要求。
2. 对每条要求检查触发条件、成功结果、失败结果、边界、状态、数据、审计、并发和恢复语义。
3. 使用等价类、边界值、决策表、状态转换、场景法、并发模型和故障注入生成测试点。
4. 设计独立、可重复的数据、手工准备步骤和环境前置条件。
5. 为每个用例写明 ID、标题、需求 ID、优先级、执行工具、执行状态、前置、明确数据、编号步骤、对应预期、清理和证据。
6. 建立“需求 ID -> 测试点 -> 用例 ID -> 手动执行方式”的追踪矩阵，并执行正向/反向检查。

硬性规则：
- 预期结果必须包含准确的响应、数据变化、版本/审计和不变项，禁止写“正常”或“正确”。
- 未定义或冲突的预期建立 TBD，写明问题、选项、影响用例和关闭条件，不得自行猜测。
- 状态型功能必须覆盖合法转换、每个非法来源状态、重复动作和闭环。
- 写操作必须覆盖成功提交、业务失败不变、数据库失败回滚和并发竞争。
- Mock 不能替代真实数据库事务、中间件、数据库时间和并发锁验证。
- 不生成自动化测试代码；自动化建设是手动用例评审稳定后的独立工作。
- 本阶段只生成手动测试用例文档，不修改生产代码、现有测试或部署配置。
```

## 12. CNAPS 审核需求示范

`docs/test-cases/cnaps-review-test-cases.md` 展示了本规范的关键落地方式：

- 把三条接口、列表规则、状态转换、审计字段、乐观锁和范围约束拆成稳定需求 ID。
- 通过状态用例覆盖“通过、退回、重复审核、退回后修改再审核”的完整闭环。
- 将 `BILL_ID + VERSION_NO` 转为双请求屏障、唯一胜者、版本只加一次和胜者审计断言。
- 将 Oracle `SYSTIMESTAMP` 转为来源检查、格式检查和操作时间窗口，而非客户端时间相等。
- 将“不新增 `CNAPS5702Q`”和 Jolt 元数据限制转为带命令、输出和评审结论的人工只读检查。
- 对非法分页参数和非空动作 Body 的未定义行为建立 TBD，没有编造预期。

这套流程不能代替清晰需求，但可以通过原子化、建模、双向追踪和门禁，让遗漏与歧义在测试执行前显性化。
